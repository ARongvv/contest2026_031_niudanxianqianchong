# openvela_smarthome 比赛任务实现与进度

> 文档日期：2026-08-10
> 用途：比赛项目进度评审、答辩材料与 PPT 制作底稿。
> 口径：严格区分“代码已实现”“自动化测试通过”“目标设备/现场演示已验证”。未有设备侧证据的能力，不作为已验收成果表述。

## 1. 项目概述

项目基于 openvela RTOS 与纯 C 语言 cAGENT 框架，构建自然语言驱动的智能家居原型。用户可在 NSH Console、LVGL 图形界面中输入家居指令；Agent 结合设备状态和领域 Skill 调用受控工具，完成灯光、空调、场景、天气及定时器等操作，并反馈工具执行过程与结果。

当前设备层为可替换的虚拟家居状态服务，已完成 ESP32-S3-BOX-3 开发板适配和 Goldfish QEMU 模拟器运行路径。系统同时预研了 OpenClaw Node 多设备协作、标准 MCP 外部工具接入，以及手机应用 HTTP/WebSocket 桥接。

```text
用户输入（Console / LVGL）
          |
          v
cAGENT：模型推理 + Skill 上下文 + 工具选择
          |
          v
本地工具 / Node 远程工具 / MCP 外部工具
          |
          v
虚拟设备状态服务（后续可替换为真实驱动）
          |
          v
工具结果、设备状态与可解释事件链反馈给用户
```

## 3. 初赛任务实现情况

### 3.1 自定义工具开发

应用当前向 Agent 注册 9 个本地工具，超过赛题“至少 2 个”的要求。

| 工具 | 功能 | 实现状态 |
| --- | --- | --- |
| `get_home_status` | 查询虚拟家居设备与环境状态 | 已实现 |
| `get_weather` | 返回结构化模拟天气数据 | 已实现 |
| `set_light` | 按房间控制灯光开关与亮度 | 已实现 |
| `set_ac` | 控制空调开关、模式、风速和温度 | 已实现 |
| `run_scene` | 执行睡眠、电影、离家、回家场景 | 已实现 |
| `set_timer` | 创建 demo 定时器/提醒 | 已实现 |
| `list_timers` | 查询当前定时器 | 已实现 |
| `cancel_timer` | 按 ID 取消定时器 | 已实现 |
| `read_skill` | 按受控 Skill 名称读取完整策略 | 已实现 |

工具实现在 `demos/smart_home/src/tools/`，设备状态与场景逻辑位于 `src/device/`。工具以 JSON 输入输出，Agent 负责模型工具调用与多轮结果汇总，设备层不直接依赖模型。

### 3.2 自然语言控制闭环

已实现并留存以下典型闭环：

```text
输入：“打开客厅灯”
  -> 模型请求
  -> TOOL_CALL set_light
  -> TOOL_RES set_light (err=0)
  -> 第二轮模型请求
  -> 回复：“客厅灯已打开，亮度设置为 80%。”
```

Goldfish QEMU 日志记录了 HTTPS 连接、两轮模型请求、`set_light` 调用和最终回复。ESP32-S3-BOX-3 的开发记录也表明，板端已完成 Wi-Fi、TLS、DeepSeek OpenAI-compatible API 和 `set_light` 的最小闭环。

当前局限：设备模型是内存中的虚拟设备，状态不跨重启持久化；定时器仅记录 demo 任务，尚不会到期自动执行真实动作。

### 3.3 可运行性、异常处理与复现

已提供 Goldfish 与 ESP32-S3-BOX-3 双平台构建、资源部署、网络配置和排障文档：

- Goldfish：以 `eth0` 联网，使用 ADB 部署 `/data/res/` 资源。
- ESP32-S3-BOX-3：以 Wi-Fi/WAPI 联网，使用 LittleFS 数据分区部署资源。
- 配置校验覆盖模型 host、path、port、model、timeout 等字段。
- 网络、TLS、HTTP、模型解析及工具错误均可向 Console/LVGL 事件链反馈。
- API key 不应写入源码或串口日志；敏感配置与普通配置模板已分离。

待收尾项：按最终提交版本重新执行一次干净构建，保存构建输出、关键命令和运行日志，作为可复现交付证据。

### A. Skill 文件编写：完成

| Skill | 覆盖场景 |

### B. 多设备协作：代码完成，QEMU 联调待验收

已实现 OpenClaw Node 协作链路：

```text
sensor_node
  -> WebSocket + shared token
  -> smart_home Node gateway
  -> 动态注册 node_* 工具到 cAGENT
  -> Agent 选择远程工具
  -> gateway 转发调用并返回结果
```

计划演示的两个节点为：

| Node | 远程工具 | 演示意图 |
| --- | --- | --- |
| `living_sensor` | `node_living_sensor_get_temperature` | 查询客厅温度 |
| `living_fan` | `node_living_fan_set_fan` | 根据指令控制客厅风扇 |

已完成：Node 协议、WebSocket transport、动态远程工具生命周期、Node gateway、sensor_node 和 host 端端到端测试。

未完成：两台 QEMU 与 gateway 的端口转发、节点上线、真实模型调用远程工具的完整演示。当前 Node gateway 文档明确记录“两节点 QEMU 演示尚未跑通”，因此本项不能按已验收表述。

### C. MCP 协议扩展：核心完成，设备侧验证待补

已实现标准 MCP Streamable HTTP tools-only Profile：设备可执行 `initialize`、`notifications/initialized`、`tools/list` 与 `tools/call`，并将 allowlist 中的 MCP 工具动态注册为 `mcp_<server>_<tool>`。

实现要点：

- 支持 HTTP/HTTPS，HTTPS 复用 openvela mbedTLS runtime。
- 支持自定义认证 header，真实凭据使用 `secrets.json` 保存。
- MCP allowlist 限制可导入的外部工具。
- MCP 发现由 Settings 页手动触发，不阻塞 LVGL 首屏。
- host 端 `mcp_bridge` mock 测试已通过。

待验证：QEMU 连接仓库 fake MCP server 的发现与工具调用、真实第三方 HTTPS MCP 的 DNS/TLS/header/allowlist 验证。当前 TLS 使用可选证书校验，不能宣称具备公网生产级安全性。

### D. 多 LLM 后端适配：配置能力完成，跨后端实测不足

Settings 页和配置层已支持以下后端 preset：

| 后端 | 默认模型 | 工具调用状态 |
| --- | --- | --- |
| DeepSeek | `deepseek-v4-flash` | 已有端到端工具调用日志 |
| MiMo | `mimo-v2.5` | 已配置，待实测 |
| Qwen | `qwen-turbo` | 已配置，待实测 |
| OpenAI | `gpt-4o-mini` | 已配置，待实测 |
| Custom | 用户填写 host/path/port/model | 已实现 |

切换 preset 可自动填充 host、path、port、model，且不会覆盖 API key；配置应用后后续 chat 使用新模型配置。

当前缺口：赛题要求“至少 2 种后端并对比工具调用表现”。应至少补测 MiMo 或 Qwen，
并按[多 LLM 后端工具调用对比测试方案](../../../docs/plans/llm-backend-toolcall-comparison.md)
冻结环境和用例，比较任务成功率、参数正确率、稳定性、首工具时间、端到端时间与异常

事件链不足以自动判定工具参数与最终状态。

### E. 安全增强：基础机制具备，应用策略未闭环

已实现的安全边界：

- 工具参数、调用次数、工具超时、输出长度都有 guard 限制。
- `read_skill` 按 Skill ID 访问，不提供任意文件路径读取能力。
- LLM 不可见设备增删改与环境模拟入口，只能由 Panel 本地操作。
- Node 使用 shared token 准入；MCP 使用 secrets 与 allowlist。
- 模型配置校验拒绝不合法 host/path/port 等输入。

当前缺口：仓库有 `policy.example.json`，cAGENT 也提供 `agent_set_policy_callback()`，但 smart_home 应用层尚未加载该文件或注册 callback。因此本地工具白名单、远程 Node/MCP 默认拒绝等策略还没有成为实际运行时准入控制，也没有相应的允许/拒绝自动化测试。

建议将本项作为复赛重点补齐：加载 policy 配置、按工具来源和风险级别决策、对拒绝请求返回结构化 `policy_denied`，并至少提供“允许本地只读工具”“拒绝未授权远程工具”两条测试记录。

## 6. 当前风险与未完成事项

### 6.1 竞赛功能风险

1. **多设备协作没有 QEMU/实机闭环证据。** 这是复赛任务 B 的主要风险。
2. **多模型仅有 DeepSeek 实证。** 预设存在不等于模型实际支持稳定 tool calling。
3. **安全策略配置尚未真正接入。** E 任务不能仅以 `policy.example.json` 作为完成依据。
4. **MCP 真实 HTTPS 仍待验证。** 需要特别关注证书强制校验、系统时间和第三方响应大小。
5. **设备仍为虚拟状态。** 不影响初赛基础闭环，但会降低开发板展示的直观性。

### 6.2 当前工作区注意事项

当前有未提交的手机 App bridge 内存/线程定位改动，包括聊天服务的配置化与默认关闭。这些改动不影响上述核心赛题完成度判断，但尚未有完整固件回归测试；在其稳定前，不应将手机 App AI 聊天作为比赛主演示功能。

### 8.2 封面、cAGENT 与项目整体架构（第 1–3 页）

**第 1 页｜项目定位：运行在 openvela 上的纯 C 智能家居 Agent**

- 核心文案：用户用自然语言下达目标，cAGENT 选择受控工具完成灯光、空调、场景、
  天气和定时器操作。
- 建议画面：项目名称、Goldfish 与 ESP32-S3-BOX-3 两个平台标识、一次“打开客厅灯”
  的输入/结果截图。
- 讲解重点：嵌入式 RTOS 上不依赖 Python/Node.js 运行时，设备层保持可替换。

**第 2 页｜cAGENT 架构：嵌入式端的 ReAct Agent 核心**

- 建议画面：以 `Agent Core` 为中心，展示 Model Provider、Session/Memory、ReAct Loop、
  Tool Registry、Skill/Context Provider、Policy、Event Callback 的关系；用
  “模型响应 → tool_calls → 工具执行 → tool_result → 下一轮模型”的环形箭头说明执行机制。
- 讲解重点：cAGENT 是纯 C 的通用 Agent 框架，负责模型调用、工具注册、上下文组织、
  多轮 ReAct 和事件观测；它不绑定某个智能家居设备或某个 LLM 厂商。
- 可引用事实：smart_home 通过 OpenAI-compatible Provider 接入模型，使用 event callback
  将模型请求、工具调用、工具结果和错误反馈给 Console/LVGL。

**第 3 页｜项目整体架构：cAGENT 在 smart_home 中的落地**

- 建议使用本文件第 1 节的架构图，展示 Console/LVGL → smart_home agent 装配层 →
  cAGENT → Skill/Tool → 虚拟设备/Node/MCP 的完整数据流，并标出 Goldfish 与 BOX-3

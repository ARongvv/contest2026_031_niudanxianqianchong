# OpenVela Git 提交流程

用于整理工作区、划分独立变更并创建可审阅的 Git 提交。适用于本项目及其可能存在的嵌套 Git 仓库。

提交标题采用 Conventional Commits 的英文前缀和作用域，后接中文描述，例如：

```text
fix(camera): 修正 CSI RAW 缓冲区同步
docs(camera): 补充 SC2336 摄像头接入指南
feat(camera): 增加视频节点注册
```

不要使用“修复：”或“文档：”作为提交标题前缀。代码注释、标题正文和提交正文使用与项目现有风格一致的中文或英文。

## 开始前确认仓库边界

1. 在预期目录和其上级目录分别执行 `git rev-parse --show-toplevel`、`git status --short`，确认当前操作的是哪一个仓库。
2. 若发现嵌套仓库，分别审查其状态；只在用户指定的仓库内暂存和提交。
3. 查看当前分支、最近提交和变更摘要：

   ```bash
   git branch --show-current
   git log -5 --oneline
   git status --short
   git diff --stat
   git diff --cached --stat
   ```

4. 保留来源不明的未跟踪文件、用户本地配置、构建产物和其他任务的改动。除非用户明确要求，不删除、重置、清理或暂存它们。

## 验证优先的变更整理

按可以独立阅读、回退和验证的目的拆分变更。一个功能、缺陷修正或
行为改变，从实现到验证通过只能形成一个提交；不能将“尝试修复”“添加
临时诊断”或“第一版实现”先提交，再以补丁提交后续修正。

对会改变构建产物或运行行为的 `feat`、`fix`、`refactor`，先定义与变更
相匹配的验收命令和通过条件。示例：驱动变更至少需要完成适用的编译，
涉及硬件数据通路时还需要板端日志证明目标行为；应用功能需要执行其
主要调用路径。纯 `docs` 变更以链接、命令和内容审查为验证；不需要虚构
运行测试。

硬件编译、烧录和板端测试由用户负责时，应在实现完成后提供精确命令、
期望输出和失败时所需日志，等待用户的实际结果。不得把“等待用户验证”
或“理论上可编译”写成已通过，也不得在验证前提交功能代码。

验证失败时：

1. 保留该功能的全部相关改动在工作区，不暂存也不提交。
2. 根据失败日志继续修改同一变更组，并再次执行完整验收。
3. 只有最终状态通过验收后，才暂存并创建一次提交。

为了保存未验证工作，可保留分支和工作区；除非用户明确要求保存诊断
快照，不以常规 Git 提交保存失败尝试。若用户明确要求提交未验证的
诊断或阶段性工作，提交正文必须说明未验证原因、风险和下一步，且不能
标记为功能已完成。

## 整理和审查已验证变更

验证通过后，再对最终变更进行审查和暂存。将实现、不可分割的配置以及
完成该功能所需的测试或文档放入同一提交；不要为了机械拆分而破坏可运行
状态。与该功能无关的 docs 或其他独立改动应另行处理。

对每一组变更：

1. 先检查未暂存差异，确认不存在秘密信息、调试残留、无关格式化或生成物：

   ```bash
   git diff -- <文件或目录>
   ```

2. 只暂存该组文件，优先显式路径：

   ```bash
   git add -- <文件或目录>
   ```

3. 审查将要提交的确切内容：

   ```bash
   git diff --cached --check
   git diff --cached -- <文件或目录>
   git diff --cached --stat
   ```

4. 发现某文件只应提交部分内容时，使用 `git add -p -- <文件>`，再次审查暂存区。不要为追求拆分而将无法工作的源码改动拆开。

## 编写提交说明

标题格式为：

```text
<type>(<scope>): <中文动宾短句>
```

常用 `type`：

- `fix`：修正已有行为、缺陷或诊断错误。
- `docs`：只调整文档、开发日志或指南。
- `feat`：增加用户可见能力或完整功能。
- `refactor`：不改变预期行为的结构整理。
- `chore`：维护性改动，且不属于以上类别。

提交正文使用中文分点说明，至少交代：

- 修改了哪些模块、文件或行为；
- 解决的问题、触发条件或设计目的；
- 已执行的检查和验收命令，以及可核对的通过结果；
- 构建或硬件验证由谁执行。功能提交中不得存在尚未完成的必要验证。

示例：

```text
fix(camera): 打通 ESP32-P4X SC2336 CSI RAW 接收

- 初始化 ISP RAW bypass，并配置 CSI Bridge 的正确行宽单位。
- 在启动 Bridge 前使能 GDMA，避免首帧丢失。
- 修正 M2C 缓冲区同步标志和对齐约束。
- 已执行 git diff --check；用户已完成 video 配置编译和 csi_probe raw 10 板端验收。
```

用临时文件保存多行提交正文，再传给 `git commit --file`，避免 shell 转义改变换行或字符：

```bash
git commit --file /tmp/openvela-commit-message.txt
```

仅当用户已明确要求提交，且该提交满足上述验证门槛时执行 `git commit`。
不要默认执行 `git push`、创建标签、合并分支、变基或修改远端。

## 提交后核对

每次提交后执行：

```bash
git show --stat --oneline HEAD
git status --short
```

报告提交号、标题、涵盖内容、验证命令及其结果，以及剩余改动的状态和归属。若用户负责构建或板端验证，报告其已提供的实际通过结果；没有结果时，功能代码应仍留在工作区而非提交。

## 交付前检查

- 每个提交只包含一个清晰、已验证的目的。
- 功能或行为变更的提交已通过对应的构建、测试或板端验收；失败尝试没有进入历史。
- 提交标题以 `fix(<scope>):`、`docs(<scope>):`、`feat(<scope>):`、`refactor(<scope>):` 或 `chore(<scope>):` 开始；不用中文类别作前缀。
- 每个暂存集都通过 `git diff --cached --check`。
- 不存在未经确认的未跟踪文件或其他任务改动被混入提交。
- 未在用户未要求时推送或改写历史。

# ESP32-P4X MIPI-DSI Host Probe 排障记录

本文记录 2026-08-21 为 `esp32p4-function-ev-board` 新增
`dsi_probe` 后，在 custom chip、custom board、NuttX Kconfig 与实板
USB Console 链路中发现的问题。本文只陈述已经观察到的事实；未完成的
DSI 命令传输测试不能视为显示功能已验收。

## 当前结论

- `usbconsole` 最小基线已在 ESP32-P4X Function EV Board 实板稳定进入
  `nsh>`；USB Serial/JTAG、`0x2000` 烧录地址及 `16MB/DIO/80MHz` Flash
  参数已经验证。
- `dsi_probe` 的 MIPI-DSI Host 与板级装配代码已成功编译并生成
  `nuttx.bin`；实板已完成 Host 初始化、GPIO27 硬件复位、generic short/long
  packet 与 EK79007 默认初始化**写**序列的 M1 验收。
- P4X 面板在当前 command-only 阶段未返回 `DCS GET_POWER_MODE (0x0a)` 的
  payload。Host 已完成 BTA 请求而 RX FIFO 为空；此结果作为诊断记录，不能用作
  命令写链路失败的依据，也不能据此宣称已经点亮显示。
- 本轮构建产生的 `.depend`、`Make.dep`、`.built` 是临时构建产物，不能
  提交到竞赛工程。
- M2a 已新增 Host 内建 DPI 色条代码及其 Kconfig 展开验证；当前工作区的完整
  固件构建被外部 `esp-hal-3rdparty` 镜像缺少
  `components/soc/esp32p4/include/soc/gpio_sig_map.h` 阻断，尚未据此宣称
  M2a 已完成编译或实板显示验证。

## 问题与处理汇总

| 编号 | 现象 | 根因 | 处理状态 |
| --- | --- | --- | --- |
| 1 | `-march=i`、`-mabi=` 导致 RISC-V 编译器拒绝执行 | custom chip Kconfig 的 `select ARCH_RV32/ARCH_RV_ISA_*` 未重新展开到旧 `.config` | 已通过 `olddefconfig` 验证配置链路 |
| 2 | 板级编译找不到 `board.h` | 私有 board header 经 `include/arch/board` 导出，不应以裸 `<board.h>` 引用 | 已修复为 `<arch/board/board.h>` |

| 4 | `savedefconfig` 报 `MIPI_DSI` 依赖 `DRIVERS_VIDEO` | `ESPRESSIF_MIPI_DSI` 选择通用 `MIPI_DSI`，未选择其父级视频子系统 | 已在芯片 Kconfig 增加 `select DRIVERS_VIDEO`，配置与构建已通过 |

| 6 | Probe 应用编译找不到 `board.h` | 应用代码同样使用了裸板级头路径 | 已修复为 `<arch/board/board.h>` |

## 1. Custom Chip Kconfig 未展开

### 现象

构建早期出现：

```text
riscv-none-elf-gcc: error: missing argument to '-mabi='
riscv-none-elf-gcc: error: '-march=i': ISA string must begin with rv32 or rv64
```

### 根因与验证

`ARCH_CHIP_RISCV_CUSTOM` 选择 `ARCH_CHIP_CUSTOM` 后，NuttX 在配置期通过：

```text
nuttx/arch/Kconfig
  → source "$BINDIR/arch/dummy/Kconfig"
  → nuttx/arch/dummy/Kconfig
```

加载 custom chip Kconfig。构建期则由：

```text
nuttx/arch/risc-v/src/chip
  → contest2026_031_niudanxianqianchong/chips/esp32p4
```

访问芯片源码。两条映射均正确；问题是旧 `.config` 没有重新执行 Kconfig
求值，缺少下列由 `ARCH_CHIP_ESP32P4` 选择的符号：

```text
CONFIG_ARCH_RV32=y
CONFIG_ARCH_RV_ISA_M=y
CONFIG_ARCH_RV_ISA_A=y
CONFIG_ARCH_RV_ISA_C=y
```

不要把这些架构选择硬编码到 defconfig。应使用正确的 openvela 环境执行
`olddefconfig`，由 custom chip Kconfig 统一导出。

## 2. Board 与 Chip 头文件边界

NuttX 为 custom board 建立：

```text
nuttx/include/arch/board
  → board/esp32p4/esp32p4-function-ev-board/include
```

为 custom chip 建立：

```text
nuttx/include/arch/chip
  → chips/esp32p4/include
```

因此板级和应用代码必须使用：

```c
#include <arch/board/board.h>
#include <arch/chip/esp_mipi_dsi.h>
```

不能依赖构建目录中 `arch/risc-v/src/board/include` 或
`chip/common/espressif` 的临时搜索路径。DSI/LDO API 已导出至
`chips/esp32p4/include/`；`common/espressif` 下的同名头仅作为芯片内部
兼容转发层。

## 3. MIPI-DSI Kconfig 依赖

通用 `MIPI_DSI` 位于 `DRIVERS_VIDEO` 子系统下。ESP32-P4 Host 需要该通用
框架，故 Kconfig 关系必须完整表达为：

```kconfig
config ESPRESSIF_MIPI_DSI
    select DRIVERS_VIDEO
    select ESPRESSIF_LDO
    select MIPI_DSI
```

仅在 `dsi_probe/defconfig` 添加 `CONFIG_DRIVERS_VIDEO=y` 能避开当前告警，
但会让其他启用 ESP32-P4 Host 的配置继续失败，故不是正式修复。

## 4. `savedefconfig` 覆盖手工 Probe 配置

工作区 `build.sh` 在构建成功后无条件执行 `make savedefconfig`，并将生成的
`nuttx/defconfig` 回写至 custom board 的源 `defconfig`。当应用 Kconfig 未被
正确求值时，它会删除：

```text
CONFIG_ESP32P4_REV_MIN_301=y
CONFIG_LVX_USE_DEMO_CONTEST2026_031_DSI_PROBE=y
```

并把手工说明头替换为“autogenerated”。缺少第二项时，`dsi_probe_main.c`
不会编译或注册，NSH 中必然提示 command not found。

在保留人工 defconfig 说明和应用选择的开发阶段，使用以下流程替代
`build.sh` 的自动保存路径：

```bash
cd ~/openvela
source build/envsetup.sh

./nuttx/tools/configure.sh -E \
  "$PWD/contest2026_031_niudanxianqianchong/board/esp32p4/esp32p4-function-ev-board/configs/dsi_probe"

make -C nuttx olddefconfig

make -C nuttx EXTRAFLAGS='-Wno-cpp -Wno-deprecated-declarations' -j2
```

构建前和构建后均应确认：

```bash
rg -n \
  'CONFIG_LVX_USE_DEMO_CONTEST2026_031_DSI_PROBE|CONFIG_ESPRESSIF_MIPI_DSI|CONFIG_DRIVERS_VIDEO|CONFIG_MIPI_DSI' \
  nuttx/.config
```

预期至少包含四个值为 `y` 的配置符号。

## 5. USB Console 复位循环的判定

主机 `dmesg -w` 中观察到：

```text
cdc_acm ... ttyACM0: USB ACM device
usb ... USB disconnect
cdc_acm ... ttyACM0: USB ACM device
```

周期约 2.8 秒，属于设备主动复位与重新枚举，不是 `picocom` 的普通 EOF
问题。之后以相同 Flash 参数烧录 `usbconsole` 基线配置，已稳定获得：

```text
nsh>
```

所以 USB 物理链路、烧录偏移和 Flash 参数已排除。恢复 Probe 应用后，若再次
复位，应比较“仅 Host 编入”和“执行 `nsh> dsi_probe` 后”的现象，再定位到
Host 静态链接增量或真实硬件初始化路径；当前不得将其直接归因给面板代码。

## 6. P4 rev3 D-PHY 时钟与 PLL 锁定

### 现象

最初实板冷启动执行 Probe 时，在面板 GPIO27 reset 之前失败：

```text
ERROR: MIPI-DSI timeout stage=phy_pll_lock ...
phy_status=00001528
dsi_probe: FAIL step=host_initialize ret=-110
```

因此该问题与 LCD adapter 5V、背光、RST_LCD 跳线或面板命令无关，根因位于
P4 DSI Host/PHY 初始化路径。

### 处理与结果

竞赛工程的 `esp_mipi_dsi.c` 已按 P4 rev3 时钟关系补齐以下步骤：

1. 启用 PHY configuration clock 与 PLL reference clock 的时钟源；
2. 选择 P4 rev3 的 `XTAL` PLL reference source，设置 reference divider；
3. 查询实际参考频率后再配置 PHY PLL；
4. 依次等待 PLL lock 和所有有效 lane 的 stop state；
5. 配置 command mode 的 clock lane、switch time、CRC/ECC、EoTP、escape/timeout
   clock 与 read timeout。

修复后的实板日志已确认：

```text
INFO: MIPI-DSI PHY clock sources cfg=6 pllref=19 ref_hz=40000000
INFO: MIPI-DSI Host ready bus=0
```

这证明 P4X 的 D-PHY/Host command-mode 初始化已通过；它不代表 DPI video 已通。

## 7. DCS 写误入读路径与读回诊断边界

### 现象和根因

引入 EK79007 的第一条初始化写 `B2=0x10` 后，曾出现：

```text
ERROR: MIPI-DSI timeout stage=read_response_fifo ...
dsi_probe: DCS command 0xb2 failed ret=-110
```

`B2=0x10` 是 DCS short write，本身不应等待面板回包。根因是 Host 根据
`mipi_dsi_msg.rx_len` 是否大于零分派读写，而通用 DCS write helper 仅需要填充
发送字段。接收字段不是写路径的协议语义，不能参与分派。

### 修复和验收结论

Host 现在只对下列明确的 data type 进入 `Set Maximum Return Packet Size → BTA →
RX FIFO` 路径：

```text
GENERIC_READ_0/1/2_PARAM
DCS_READ_0_PARAM
```

所有其它 data type 均走纯发送路径。实板随后通过：

```text
dsi_probe: EK79007 DCS initialisation writes accepted
dsi_probe: PASS command Host validation completed (DCS read=unavailable)
```

当前 `GET_POWER_MODE` 的寄存器快照为：

```text
int_st0=00000000 int_st1=00000000
phy_status=000015bd cmd_pkt_status=00050015
```

其中 `gen_rd_cmd_busy=0`、`gen_pld_r_empty=1`：Host 已完成 BTA 读请求，但 RX
payload FIFO 为空。该面板当前未提供标准 DCS read response；在没有 DPI video
证据前，不将它解释为“屏幕正常”或“硬件必然断线”。

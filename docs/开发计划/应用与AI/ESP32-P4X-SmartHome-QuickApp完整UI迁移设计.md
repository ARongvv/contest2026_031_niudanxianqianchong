## 1. 设计范围

QuickApp 首期采用一个 1024 宽的单入口面板，由底部导航切换一级页面；这样可以先验证
页面布局、原生 Feature 数据与触控路径，不依赖尚未验证的多页面路由生命周期。后续可在
RPK 验证通过后拆分为独立路由页面，视觉与数据边界不变。

```text
屏保（点按 / 上滑提示）
  └─ 首页
      ├─ 设备（空间筛选） ── 设备详情
      ├─ 场景
      ├─ 安防
      └─ 更多 ── 系统设置
```

首页保持“左侧环境大卡 + 右侧异构卡片”布局，顶部仅保留隐私/网络/时间状态，不显示房间
Tab 或首页编辑模式。房间筛选只位于设备页；底部固定为“首页、设备、场景、安防、更多”。

## 2. 页面与数据状态

| 页面 | 首期交互 | 数据状态 | 后续 Native Feature |
| --- | --- | --- | --- |
| 屏保 | 点按进入首页 | 本地时钟/静态环境摘要 | 时钟、天气、壁纸资源 |
| 首页 | 主灯开关、进入各入口 | 主灯为真实状态；其余摘要显式标注待接入 | 环境、场景、媒体、家庭摘要 |
| 设备 | 全部/客厅/卧室/厨房/卫生间筛选 | 主灯真实；其他设备为计划卡 | 设备目录、能力、状态订阅 |
| 设备详情 | 主灯开关、亮度展示 | `setPower` 真实；亮度精调禁用说明 | `setBrightness`、色温、空调/窗帘能力 |
| 场景 | 展示场景与执行入口 | 不声明已执行 | `runScene` 与权限确认 |
| 安防 | 摄像头预览占位、布防状态 | 不显示伪造视频帧 | 原生视频平面、门磁、人体、告警确认 |
| 系统设置 | 网络、LLM、工具、Skill、健康面板 | IPC/状态版本真实；其余按配置状态呈现 | 系统状态、模型配置、工具与 Skill 清单 |

`sim-living-room-light` 是唯一 P0 真实设备。页面通过 `system.smarthome` 读取其 snapshot，
并只以 `controlDevice(setPower)` 的原生确认结果更新开关。若 Feature 不可用，页面保留
完整布局但显示“不可用”，不会回退到 JavaScript mock。

## 3. 视觉与交互规则

- 主题为 `light-calm`：暖灰画布、暖白卡片、鼠尾草绿作为低饱和激活色；不使用实时模糊。
- 触控目标至少 68×56 px；底栏 64 px；卡片间距约 12 px；卡片圆角 18 px。
- 摄像头仅使用深色预览占位。真实预览只能在 Native 视频路径具备表面/帧同步能力后替换。
- “真实服务”“待接入”“计划接入”是工程状态，不是最终用户文案。完成对应 Feature 后应
  改为设备/服务真实状态，并在产品版本中隐藏开发标识。
- 高风险动作（撤防、门锁、删除自动化）不在首期快捷卡直接执行；必须走原生权限确认。

## 4. 资源策略

本次 UI 骨架仅使用文本符号和 CSS 色块，目的是先验证布局和数据闭环。正式资源接入时：

1. 状态与导航图标从统一 SVG 源稿导出为 PNG WebP/RPK 可用的位图尺寸；
2. 1024×600 面板优先准备 20、24、32、48、96 px 五级图标，而非每页各自缩放；
3. 屏保壁纸采用压缩 JPG；摄像头缩略图由 Native 生成低频位图；
4. 不把实时视频、SVG 解析或全屏高斯模糊放到 QuickApp JS 渲染链路。

## 5. 验收顺序

1. 先验证 RPK 可启动、屏保可进入首页、底栏与每个一级页面可切换；
2. 验证主灯 snapshot、开关、旧 revision 刷新和服务不可用提示；
3. 验证 1024×600 下的文字、卡片、GT911 触控命中与页面滚动；
4. 记录 UI 切换和主灯控制的帧率，复杂交互页以稳定 30 FPS 为目标；
5. 最后逐项替换“待接入”卡片，禁止用演示数据掩盖原生能力缺失。

RPK 尚未在当前环境打包，因此本文中的 QuickApp UI 属于待用户验证的阶段性成果；不应称为
已完成的模拟器或 P4X UI 验收。
